How the conversion became faster

Five stages, measured with the ultrasound test set: 212 files, 15 335 frames, Mac with an Apple chip and 10 cores. After stages 1–4 all outputs are the same as before – movies in the video stream, everything else byte for byte. Stage 5 encodes the movies with a faster setting: same size, image fidelity minimally lower.

1Read only the frames that are needed

Before the actual encoding, the DICOM-Converter looks at individual frames of a movie:

  • the last frame, to cut the cover patches from it once per device and day (mask cache),
  • the first and last frame for the second-name search and the generic text recognition.

Before, forEachFrame ran over the whole movie with a window size of 1 for this; only frame 0 or frame n−1 was kept. A loop with 150 frames was therefore decoded completely to get two images. On top of that, DCMTK creates a separate DicomImage instance for each window and checks the color model by decoding on a trial basis. So every frame was in effect decoded twice.

Now, framesAt(ds, {0, n−1}) jumps directly to the fragments of these frames in the encapsulated pixel data and decodes only them. That alone took away almost half of the run time.

2libjpeg-turbo instead of DCMTK for JPEG Baseline

Almost all ultrasound movies have the same form – 93 % of the frames in the test set:

PropertyValue
Transfer syntax1.2.840.10008.1.2.4.50 (JPEG Baseline)
Bit depth, components8 bit, 3
Photometric InterpretationYBR_FULL_422 or YBR_FULL
Fragmentsexactly one per frame

DCMTK’s JPEG decoder (dcmjpeg) is its own copy of the old IJG libjpeg 6b – clean, but scalar. libjpeg-turbo uses the CPU’s vector unit (SIMD: NEON on Apple chips, SSE2/AVX2 on Intel/AMD) for the three expensive steps: the inverse DCT of the 8×8 blocks, upsampling the halved color channels with 4:2:2, and the conversion YCbCr → RGB. It computes 8 or 16 values at once.

Keeping the pixels the same

  • Color space forced: cinfo.jpeg_color_space = JCS_YCbCr. With YBR_*, DCMTK ignores the JFIF and Adobe markers in the JPEG stream and always computes YCbCr → RGB. Otherwise libjpeg-turbo would follow the markers.
  • The same IDCT: the integer JDCT_ISLOW, not the faster, less precise floating-point or “fast” variant.
  • The same upsampling: “fancy upsampling”, as preset in DCMTK.

Both are based on the same IJG computation, so the very same RGB image comes out bit for bit. The unit test test_framesource checks this pixel by pixel against DCMTK; comparing all outputs confirmed it.

Falling back to DCMTK. The fragments are not copied: FastJpeg only holds pointer and length into DCMTK’s pixel sequence. A separate error manager catches errors with setjmp/longjmp. With a broken frame or different dimensions, DCMTK takes over this frame. JPEG-LS, JPEG 2000, Lossless, RLE, uncompressed data and several fragments per frame go through DCMTK anyway. With DCMCONV_DCMTK_JPEG=1 the fast path is switched off completely.

3Decoding ahead in two helper threads

A classic producer–consumer pattern in forEachFrame:

Helper thread 1decodes frame i
Helper thread 2decodes frame i+1
→
Queueat most 6 frames ahead
→
Main threadstrictly in order: filter (libavfilter), encode (x264)

Each helper thread fetches the next frame number and decodes into a buffer of its own; the result goes into slot slots[k] = frame first + k. The main thread takes the frames in order and only waits if the next one is not ready yet. If an error occurs, the threads are stopped, and from exactly this frame on processing continues one after the other, with DCMTK as the fallback.

The gain is small (2:21 → 2:12): after stage 2 decoding is already cheap, encoding dominates, and x264 already uses several threads itself. As a side effect, memory use dropped from 1.87 to 1.31 GB.

4Several files at the same time

One after the other, only a little over half of the 10 cores were busy on average: x264 does not use everything with short loops, and reading and text recognition run single-threaded. With three lanes the cores are almost fully used; more lanes only cost memory, about 0.4 GB per lane.

Why the results stay the same

Decoding, filtering, encoding and text recognition depend only on the one file and give the same result no matter when and in which thread they run. x264 is also deterministic with the same settings, and every file gets the same settings as before.

Everything with shared state goes through an ordered gate (takeTurn → releaseTurn): file k only gets in once file k−1 has left it. This concerns patient folders and “(2)” for identical names, the mask cache per device and day, series counters and identical output names.

Gate – strictly one after the otherComputing work – at the same timewaiting for the gate

Ultrasound files leave the gate early: as soon as the output path is fixed (claimAndRelease), the next file may enter while the first is still encoding. CT, MRI and fluoroscopy stay in the gate until the end of the file, because a series is built from many files with shared state. That is why they hardly gain.

Log and side effects in file order

Anything that only takes effect at the end of the run – PDF destinations, samples, folder date and Finder tags, glue candidates – is collected by each file in a FileRecord of its own, as are its log lines (captured with log::Capture). The main thread commits the records in file order (commit). That is why the log and the counters are identical line for line as well.

In short: the process behaves as it used to one after the other; only the pure computing work overlaps. --jobs 1 (or DCMCONV_JOBS=1) takes exactly the old route without lanes and is identical to 3.0.0.373.

5Faster encoding: x264 “veryfast” instead of “medium” since 3.0.0.389

After stage 4 the computer is fully loaded, with 8.6 of 10 cores working on average. Sampling during the conversion shows what for: 88 % of the computing time goes into the H.264 encoder x264, reading and color conversion together less than 4 %. More files at the same time therefore no longer help (3, 5 and 7 lanes: 16.9 / 17.2 / 17.5 s on a subset). The lever is the encoder itself.

x264 has presets from “ultrafast” to “placebo”. They determine how thoroughly it searches for motion between frames and how many earlier frames it uses as references. The quality level (CRF 18) stays the same, and x264 adjusts the amount of data accordingly. Across all 92 movies of the test set:

PresetTimeSizePSNRSSIM
medium (up to 3.0.0.388)1:36 min385 MB48.8 dB0.9946
faster≈ 1:07 min401 MB48.3 dB0.9940
veryfast (since 3.0.0.389)0:53 min385 MB47.5 dB0.9931

PSNR and SSIM measure the distance to an almost lossless version (CRF 1) of the same conversion; above 40 dB a difference is considered practically invisible. “veryfast” halves the time at the same size and costs a good 1 dB; a difference amplified tenfold shows slightly more fine noise. “faster” (time extrapolated from a subset) even gets larger, because it uses fewer earlier frames as references without saving much time.

Switching it off: --encoding thorough in the terminal or DCMCONV_X264_PRESET=medium encodes as up to 3.0.0.388. The log states the choice in the line about the encoded movies. Hardware encoders (VideoToolbox) were not faster than “veryfast” and give different results depending on the computer.

Checked on the entire test collection (6.5 GB, 758 outputs): old version = one after the other = at the same time, also with glue and the anonymization check, in the Windows VM and in the Intel part under Rosetta. All test data: 326 s → 197 s; with glue and check 919 s → 409 s.
