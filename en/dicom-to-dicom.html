DICOM to DICOM: what exactly happens

With the output format DICOM (right-click “DICOM – anonymize to DICOM”, in the terminal --preset dicom), every suitable image file becomes a DICOM file again. Name and ID are replaced by a random code, the header is cleaned according to the standard DICOM PS3.15, and the storage contains no names. This explanation is based on the source code and test runs; the examples contain no patient data.

  • Ultrasound: patient data shown in the image is covered. Outside the covers there is no new compression loss. With JPEG only the affected blocks are replaced.
  • CT, MRI and others: the image stays unchanged; only the header is cleaned.
  • When in doubt, no output: if DICOM is not possible, nothing is created – no MP4 or PNG either. The reason is in the log.

The result is pseudonymous, not completely anonymous. Examination date, age, device including serial number and the (cleaned) descriptions are kept on purpose. Together they may allow conclusions. Section 10 lists the limits.

1The process at a glance

Each file is loaded and its header read (the character set becomes UTF-8), then the code and the target folder are determined. After that the program decides step by step:

Questionyesno
Image storage class with pixel data?continueno output (PDF, structured report …)
Ultrasound (or a nuclear medicine screen capture)?continueimage unchanged, only the header is cleaned (text recognition only for screenshots or “Burned In Annotation: YES”)
Matching device rule?continuetext recognition finds the data, covers it, checks again; otherwise no output
Rule with covers?insert the covers, compare with the original outside themrule only crops: no output; rule without covers and cropping: image unchanged

Finally the header is cleaned and the file written. In the output format DICOM, anonymization cannot be switched off by a profile. If it is switched off with an option (--no-overlay), ultrasound gives no output. Missing header data such as manufacturer or model is completed for device recognition from neighbouring files of the same series or study. If only the manufacturer can be recognized from the UID, the file counts as “device unknown” and goes through text recognition.

Folder and file names contain no names, dates, IDs, institutions or examination types.

  • File date: that of the conversion, not of the examination.
  • IM number: the Instance Number from the header.
  • No identity file: the hidden file otherwise placed in the patient folder is left out, because its check values could be calculated back.

3Code and UIDs

Code. Each patient gets a code made of ANON- and eight random characters, without the easily confused characters 0, O, 1 and I. It is not calculated from the patient data.

  • Assignment: the same combination of patient ID, name and date of birth gives the same code within one run. The program would rather separate too much than merge two patients.
  • Without data: if all three values are missing, there is one code per study.
  • A later run assigns new codes. Follow-up examinations can only be matched within the same run. No assignment list is stored.

UIDs. All fields marked “U” in the standard’s table get new UIDs that cannot be derived. Within one run the same old UID always maps to the same new one, so series and references stay together.

4The DICOM header

Order of the steps

  1. Character set: on reading, the data set is converted to UTF-8. Afterwards it says (0008,0005) ISO_IR 192.
  2. Keep the age: if (0010,1010) is missing, it is calculated from the dates of birth and examination before the date of birth disappears.
  3. Clean the descriptions: name, patient ID, other IDs, accession number and date of birth (in every usual spelling) as well as the names of physicians and operators from the header are searched for in the descriptions and removed; the rest stays (“CEUS Leber MUSTERMANN” → “CEUS Leber”). The search works word by word: “Leber” stays even for a patient called “Lebert”.
  4. Copies of the date of birth: every date field with the same value is emptied, also in sequences. Some devices write the date of birth into other fields.
  5. Cleaning: each element is treated according to the table below, recursively in sequences.
  6. File meta information: sender, receiver and private information of group 0002 are removed.
  7. Newly set: code and marking (below).

Rules

The rules come from table E.1-1 in DICOM PS3.15; a script generates 402 entries from it.

ActionEntriesEffect and examples

The code 113100 (Basic Profile) is deliberately not set: the descriptions are only cleaned of known data from the header; the program does not recognize other data in them.

5The ultrasound image

Where the cover comes from

The rule set defines rectangles for each device and resolution. For each rectangle a patch is made from the first image of the movie (up to 3.0.0.403 from the last one) by continuing an image strip defined in the rule. The same patch is inserted into all images. The output format DICOM never crops. Nuclear medicine screen captures with a device rule are covered in the same way.

Treatment by transfer syntax

Transfer syntaxProcedureChecked
JPEG Baselineonly the blocks under the covers are replacedDCT coefficients outside
uncompressedpixels replaced directlypixels outside
RLE, JPEG Losslessdecode, replace, re-encode losslessly in the same syntaxpixels outside
JPEG 2000decode, replace, always re-encode losslessly, even for a lossy original. The file gets larger, but there is no second losspixels outside
JPEG-LS, video, othersno output–

Except for JPEG Baseline there are further limits: 8 bit only, 1 or 3 channels, no subsampled colour. Otherwise there is no output.

JPEG Baseline in detail

  1. The coefficients of the original image are read without decoding.
  2. The image with the cover inserted is encoded once completely, with the same quantization tables and the same subsampling. This result only serves as a source.
  3. Only the blocks in the MCU grid that cover the rectangles are taken over from it into the original.
  4. The original coefficients including the replaced blocks are written. The Huffman tables are recalculated.
  5. Both data streams are compared block by block. If a block outside differs, the output is discarded.

Strictly speaking: the coefficients outside are identical, but the data stream itself is not, because the Huffman coding is new. After decoding, individual pixels may also differ minimally (measurement in section 9), probably because upsampling of the colour channels works across block boundaries. This does not mean a loss of quality.

Ultrasound without a device rule: text recognition

  1. A search list is made from the header: parts of the name, patient ID, other IDs, accession number, date of birth in usual spellings. If it is empty, there is no output.
  2. The first image is read by text recognition and compared with the list (the header line with the patient data does not change in a movie). Manufacturer and model names stay.
  3. If nothing is found, the file is held back; an unchanged sample goes into the folder unsupp_res.
  4. Only the matches are covered, losslessly as above.
  5. The finished file is read again and checked again. Remaining matches are added and the original is processed once more, at most two rounds. If anything remains readable, the output is deleted.
  6. The log reports “generisch anonymisiert – bitte prüfen” (generically anonymized – please check).

6CT, MRI, PET, X-ray and others

The image is not touched, any transfer syntax is possible, the pixel data stays byte for byte the same. All images of a series are taken over, including localizers.

Text recognition only runs for screenshots (Secondary Capture) and for sources with “Burned In Annotation: YES”. The first image is checked; if something is found, the file is not taken over. Because the image otherwise stays unchecked, this path sets neither “Burned In Annotation: NO” nor the code 113101.

7When there is no output

  • PDF documents in DICOM, structured reports, presentation states and other objects without an image class
  • Ultrasound with an unsupported transfer syntax or bit depth
  • Device rule that only crops, or a result that changed outside the cover
  • Anonymization switched off (--no-overlay) or generic path switched off (--no-generic-redact) without a matching rule
  • Text recognition: no search terms, nothing found, or still readable after two rounds
  • Screenshot or burned-in image with a match in text recognition
  • ImageType contains INVALID; ultrasound without Series Instance UID; manufacturer empty

10Limits and residual risks

  1. Descriptions are only cleaned of what is known. The search covers name, IDs, date of birth and the names of physicians and operators from the header. Other data in a description (names of relatives, addresses) is not recognized. If a patient’s name is a medical term, that word disappears from his or her descriptions.
  2. Device and date help identify. Serial number, station name and the exact examination date may make an institution or examination recognizable.
  3. Device rules are not re-checked. On the path with a rule no text recognition runs. “Burned In Annotation: NO” is a statement from the rule, not a measurement in the image. If a device shows data in a different place after an update, this is not noticed here.
  4. Text recognition only knows the header. It searches for the values from the header and only in the first image. It does not find other names or data.
  5. CT and MRI without image check. Without Secondary Capture and without “Burned In Annotation: YES”, the image is not checked. For a multi-image object the burned-in path only checks the first image.
  6. Traces on your own computer. The log names source and output and so allows an assignment. unsupp_res contains unchanged samples with patient data.
Basis: source code and test runs; measurements from 31.10.2026 (3.0.0.273), process as of 3.0.0.442. The output format is also checked by an automatic test in every test run of the program.
